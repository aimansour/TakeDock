# TakeDock Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox syntax for tracking.

**Goal:** Deliver, test, and automatically publish an accessible Windows
application for fast Open Camera control and safe Android video management.

**Architecture:** Svelte 5 components using native HTML controls call a Rust Tauri
engine. Independent workers own persistent ADB command dispatch, event-driven
Android observation, asynchronous verification, and file transfers.

**Tech Stack:** Current compatible stable Tauri 2, Rust, Svelte 5, TypeScript,
Vite, Vitest, WebdriverIO with external `tauri-driver` and Edge WebDriver,
Java 17, Android SDK 37, Android Gradle Plugin, GitHub Actions.

**Spec:** `docs/superpowers/specs/2026-09-30-takedock-design.md`.

## Global Constraints

- Windows 10/11, Android 16/17, one externally authorized ADB phone.
- MIT license; English repository defaults; essential Arabic user guides.
- Phone video directory: `/sdcard/DCIM/OpenCamera`.
- Success is silent by default; Settings can enable the success sound.
- Failure sounds are enabled by default; no unsolicited spoken announcements.
- Verification never blocks later recording commands or the desktop interface.
- No XML dump, accessibility polling, screen-reader suppression, or toggle retry.
- Updates are checked automatically; installation requires explicit user action.
- GitHub publishes automatically only after successful required checks.
- Windows Desktop E2E is a required release check using the real Tauri/Rust
  application and a deterministic external ADB fixture, independently of
  real-phone and NVDA verification.
- Plain Svelte with Vite; no SvelteKit route announcements or SSR.
- Recording dispatch never waits for a Svelte effect, `tick()`, or DOM flush.
- Test drivers, fixtures, and test-only IPC hooks are not release resources.
- Do not record unlock credentials, device identifiers, personal files, or keys.

## Review Focus

- Rapid start/pause/resume/stop commands: delayed events cannot rewind newer intent.
- Connection replacement: stale jobs must never act on another phone or session.
- Filenames with Unicode, apostrophes, newlines, traversal, and Windows device names.
- Transfer cancellation, checksum mismatch, and disk failure: retain the original.
- Phone accessibility services and desktop focus remain usable through state changes.

- `docs/`: bilingual user guidance and English engineering/test evidence.

The Rust model defines `RecordingState = Unknown | Idle | Recording | Paused`,
`RecordingAction = Start | Stop | Pause | Resume`, and
`Settings { language, destination, adb_path, success_sound, verification_ms }`.
The exact Settings defaults are English, empty destination, automatic ADB
discovery, `success_sound: false`, and an initially conservative background
verification deadline adjusted using measured device timings.

Observer protocol version 1 provides `ready`, `state`, and `error` messages.
A state message includes `session`, `seq`, `event_time`, `foreground`,
`video_mode`, and `state`. Tauri emits `session-state`, `verification-result`,
`file-job`, and `operation-error` events with typed payloads.

## Frontend compatibility and testing layers

The investigated compatible baseline is Svelte 5.57.1, Vite 8.3.1,
`@sveltejs/vite-plugin-svelte` 7.3.1, `svelte-check` 4.7.6, and TypeScript
6.0.3. The latest TypeScript 7.0.2 is outside that checker's declared peer
range. Recheck current stable versions at execution, keep all peer ranges
satisfied, and commit lockfiles. Do not use forced peer installs or suppress
component checking to obtain a newer version number.

Use Rust/unit tests for transport, state reconciliation, path safety, and
file integrity; Vitest for controllers and Svelte component behavior; and
the focused Desktop E2E task below for real executable/WebView2/IPC integration.
Real Android and NVDA checks remain separate acceptance evidence. A browser
component test is not reported as Desktop E2E or a screen-reader audit.

## Execution choice

Recommended: native execution in this session, with a final independent
review. Observer feasibility and desktop protocol integration benefit from
one implementer preserving their shared state; there is no existing codebase
to divide safely before those interfaces are proven.

Alternative: subagent-driven execution with an implementer and independent
reviewers for each component, followed by a whole-project review.
